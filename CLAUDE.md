# CLAUDE.md

Рабочие заметки по проекту. Читай перед тем, как что-то менять.

## Что это

Electron-приложение: спортивная телепрограмма поверх IPTV-плейлиста. Окно приложения — только лента матчей по турнирам с кнопками каналов, прижатая к левому краю экрана; VLC играет поток в своём отдельном, независимом окне ОС рядом (не встроен и не «пришвартован» — см. «Плеер: VLC вместо hls.js» ниже, там же история, почему не встроен). Русский интерфейс, пользователь — один, дистрибутив под Windows.

Запуск: `npm start`. Сборка: `npm run dist`.

## Текущее состояние: расписание из FotMob, каналы — через сопоставление с EPG

Первая версия брала расписание матчей из недокументированного API Sofascore — направление закрыто, актуальные пути отдавали 404. Код Sofascore (`sofascore.js`, `resolver.js`) и завязанная на него ручная привязка каналов (`alias:*` IPC, диалог «Привязать канал») удалены.

Вторая версия строила расписание, слепо разбирая заголовки передач EPG (`parseFootballTitle` — набор паттернов + стоп-слова на другие виды спорта и повторы). Работало, но криво: без внешнего источника расписания нет ни точных названий команд, ни счёта, ни статуса «идёт сейчас» надёжно, а сам разбор — вечная калибровка по стоп-словам. Пользователь явно попросил «перевернуть» модель: сначала мета из внешнего источника, потом привязка к каналам.

Третья версия (первая с внешним источником меты) взяла для этого ESPN — подробности выбора и что именно проверялось см. ниже. Прожила до тех пор, пока не понадобились кубки/суперкубки Бельгии, Португалии, России, Турции и Первая лига России (ФНЛ) — их в ESPN просто нет ни под каким слагом (проверено полным перебором). Отдельное исследовательское задание («какие источники вообще использует комьюнити для такой задачи») нашло **FotMob** — у него нашлись все недостающие турниры, и пользователь попросил перейти на него полностью, а не держать два источника разом.

**Текущая модель:** `electron/fotmob.js` тянет расписание/счёт/статус с публичного JSON-API FotMob (`www.fotmob.com/api/data/...`, без ключа и аккаунта) для фиксированного списка турниров; `electron/epg.js` только ищет, на каких каналах плейлиста идёт уже известный матч (по времени + именам команд), парсинг заголовков «вслепую» не нужен.

### Почему не Sofascore, не TheSportsDB, не ESPN

Каждый вариант проверялся живьём, не в теории:
- **Sofascore** — изначально казалось, что дело только в TV-эндпоинтах (404), но при повторной проверке (для этого же исследования источников) выяснилось, что **весь** `/api/v1/*` отвечает честным `{"error":{"code":404,"message":"Not Found"}}` от их же бэкенда (не блокировка — домен и `api.sofascore.com/` живы, отдают 200) — включая общий `sport/football/scheduled-events/{date}` и `config/unique-tournaments`, задокументированные в проектах сообщества. Направление закрыто ещё жёстче, чем думали изначально.
- **TheSportsDB** — весь домен (даже обычная главная страница) отдаёт Cloudflare-блок «Sorry, you have been blocked» из любого источника, включая браузер пользователя. Не вопрос ключа — сайт недоступен для автоматических (и не только) запросов в принципе.
- **API-Football** — рабочий вариант, но требует регистрации и API-ключа; пользователь попросил обойтись без аккаунта. По той же причине отклонён и **football-data.org** — при этом даже на его бесплатном тарифе нет кубков Бельгии/России/Турции и ФНЛ, так что ключ пришлось бы заводить не ради решения проблемы.
- **WhoScored** — сайт открывается, но с фингерпринт-скриптом защиты на главной странице; чистого JSON API никогда не было, все инструменты сообщества либо гоняют настоящий браузер (Selenium/Playwright), либо парсят обфусцированный JS прямо со страницы. Не подходит под стиль проекта (простой `fetch` без браузерной автоматизации).
- **sports.ru** — ни одного упоминания в комьюнити-проектах, ни задокументированного, ни угадываемого API.
- **ESPN (site.api.espn.com)** — работал хорошо, был основным источником до этого. Минус нашёлся только когда понадобились не топ-лиги: ни кубков/суперкубков Бельгии, Португалии, России, Турции, ни Первой лиги России в нём нет ни под одним проверенным слагом (полный перебор вариантов, все отвечали HTTP 400).
- **FotMob (www.fotmob.com/api/data/...)** — неофициальный (undocumented), но так же не требует ключа/аккаунта и не подписывает запросы (в отличие от некоторых других эндпоинтов на том же домене, которые сообщество отмечает как сломанные после добавления FotMob подписи `x-mas`, — но `api/data/matches` и `api/data/leagues` от этого не пострадали, проверено живьём). Покрывает и все турниры, что были в ESPN, и все, которых там не было. Тот же риск, что был у Sofascore/ESPN (может сломаться без предупреждения) — пользователь снова пошёл на это осознанно.

### Турниры (`electron/fotmob.js` → `COMPETITIONS`, хардкод id FotMob)

Лиги: АПЛ, Чемпионшип (Англия, 2-й дивизион), Ла Лига, Серия A, Бундеслига, Лига 1, Лига чемпионов, Лига Европы, Лига конференций, Примейра-лига (Португалия), Эредивизи (Нидерланды), Про-лига (Бельгия), РПЛ, Суперлига (Турция), MLS.

Кубки/суперкубки: Кубок и Суперкубок Англии (Community Shield), Кубок английской лиги (EFL/Carabao Cup), Кубок и Суперкубок Испании, Кубок и Суперкубок Италии, Кубок и Суперкубок Германии, Кубок и Суперкубок Франции, Кубок Нидерландов, Кубок и Суперкубок Бельгии, Кубок и Суперкубок Португалии, Кубок и Суперкубок Турции — все девять пар, которых не было в ESPN, теперь на месте.

**Россия — все турниры, что знает FotMob**, не только РПЛ + Кубок (явная просьба пользователя): РПЛ, Кубок России, Суперкубок России, Первая лига (ФНЛ), Стыковые матчи РПЛ (плей-офф РПЛ↔ФНЛ), Вторая лига (3-й дивизион).

Бразилия, Аргентина, Беларусь — только главная лига + главный кубок каждой (не «все турниры», как у России — так не просили): Серия A + Кубок Бразилии, Лига Профессионал + Кубок Аргентины, Премьер-лига + Кубок Беларуси.

**Квалификации ЛЧ/ЛЕ/ЛК — отдельные турниры на FotMob**, не то же самое, что «Лига чемпионов»/«Лига Европы»/«Лига конференций» с других id. У основных турниров основной этап начинается позже (сентябрь), и на момент добавления они всё ещё стояли на прошлом сезоне (`selectedSeason` у FotMob не обновился) — расписание было пустым, из-за чего показалось, что еврокубков нет вообще, хотя вся текущая активность (плей-офф квалификации) шла именно в отдельных Qualification-турнирах (id `10611`/`10613`/`10615`), которых в `COMPETITIONS` не было. Плюс Кубок Либертадорес (`id: 45`, сезон по календарю South America, `selectedSeason: "2026"`) — отдельной квалификации под него на FotMob нет (в отличие от УЕФА), ранние раунды идут в том же id.

**Баг попутно найден и исправлен**: `COUNTRY_NAMES[code] ?? code ?? null` не отличал «код замаплен на `null` осознанно» (INT — без префикса страны) от «кода вообще нет в таблице» — `??` реагирует на `null`/`undefined` одинаково в обоих случаях. Карточки еврокубков показывали «INT - Champions League Qualification» вместо просто «Champions League Qualification». Баг существовал с самого появления фичи «Страна - Лига», просто не проявлялся: у ЛЧ/ЛЕ (`id 42`/`73`) в окне синка ни разу не было матчей до сегодняшних квалификаций. Исправлено явной проверкой `code in COUNTRY_NAMES` вместо `??`.

Полный список id проверен живьём по `https://www.fotmob.com/api/data/allLeagues` перед добавлением — то же правило, что было при подборе слагов ESPN: не гадать, всегда сверяться с реальным ответом.

У Италии два разных id с похожими именами — `222` («Super Cup») и `11015` («Supercoppa Italiana») — на деле первый мужской (Napoli/Milan/Bologna/Inter в реальных матчах), второй женский. В `COMPETITIONS` используется `222`.

### Как устроено сейчас

`electron/fotmob.js` — `fixtures(daysBack, daysForward, onProgress)` дёргает `www.fotmob.com/api/data/leagues?id={id}` на каждый турнир из `COMPETITIONS` и берёт `fixtures.allMatches` (fallback на `overview.matches.allMatches`, оба поля видел на разных турнирах с одинаковым содержимым). В отличие от ESPN здесь нет параметра диапазона дат — эндпоинт всегда отдаёт весь текущий сезон целиком, окно `[сегодня-daysBack, сегодня+daysForward]` применяется на своей стороне, после разбора ответа. Логотипы команд/лиг — не отдельный запрос, а детерминированный статический путь: `images.fotmob.com/image_resources/logo/{teamlogo|leaguelogo}/{id}.png` (проверено живьём, включая герб РПЛ — актуальный, никакого оверрайда вроде того, что был нужен для ESPN, не потребовалось). Работает только через `electron.net.fetch` (стек Chromium) — обычный `fetch`/`Invoke-WebRequest` с этого же хоста тоже блокируется (тот же класс защиты, что у Sofascore/TheSportsDB).

`electron/epg.js` не менялся под эту миграцию:
- `loadXmltv(url)` — скачивание + дисковый кэш на 6 часов, путь через `store.root`.
- `programmes(xmlText, channels)` — плоский список передач на **всех** каналах, что есть в плейлисте (`channelId, title, start`), отсортированный по времени, без попытки понять из заголовка, что это за матч. Раньше отбирал только «спортивные» каналы по эвристике (номер группы `9.`/имя группы или канала со словом sport/спорт) — убрано целиком по просьбе пользователя: эвристика была откалибрована под одного провайдера (у другого, например Antifriz, спортивная группа называется просто «Спорт» без номера) и всё равно пропускала матчи на нейтральных каналах (сборная на Первом, Кубок Германии на ARD — ни то, ни другое не назвать «спортивным» ни по имени, ни по группе). Реальный отбор «это матч или нет» и так делает `findBroadcastChannels()` ниже — сканировать все каналы дороже по CPU, но на живом прогоне (3962 канала вместо 668, ~217k передач вместо ~46k) время синка не изменилось заметно, а трансляций находится больше (было 97, стало 122 на одном и том же плейлисте).
- `findBroadcastChannels(progList, home, away, kickoffMs)` — для уже известного матча ищет передачи в окне ±90 минут от начала, где заголовок называет **обе** команды (через `normalize.tokens()`/`similarity()` — то же, что раньше матчило имена каналов). Достаточно совпадения «отличительного» слова названия команды, не всех токенов сразу — см. ниже почему.

`electron/sync.js`: `fotmob.fixtures()` → для каждой фикстуры `epg.findBroadcastChannels()` → `guide.json` в прежней форме (`days → tournaments → events → broadcasts`), так что `main.js`/`renderer` не менялись вовсе — интерфейс между источником меты и остальным приложением остался тем же, что был у `espn.js`. Окно расписания — вчера + 6 дней вперёд (`DAYS_BACK`/`DAYS_FORWARD` в `sync.js`); дальше EPG-фид всё равно не заглядывает (~4–5 дней вперёд), так что у поздних фикстур `broadcasts` пока пустой — это нормально, не баг.

Полный прогон (37 турниров, ~16 секунд, живой плейлист) не дал ни одной ошибки; ФНЛ и найденные ранее недостающие кубки уже строят карточки с трансляциями.

### Грабли конкретно с сопоставлением команд

Требовать совпадения **всех** слов названия команды — ломает почти всё для России: ESPN пишет `"CSKA Moscow"` (английский экзоним), а наша транслитерация кириллицы «Москва» даёт `"moskva"`, не `"moscow"` — эти строки никогда не совпадут. Из-за этого при первой версии `findBroadcastChannels` **все** матчи РПЛ давали 0 трансляций. Исправлено: `teamInTitle()` требует совпадения `max(1, слов - 1)` — то есть для двусловных имён достаточно одного (как правило это и есть отличительное слово: «cska», «lokomotiv», «spartak»), город/уточнение можно не поймать. Проверено на живом прогоне: РПЛ, Турция, MLS находят трансляции корректно.

**Баг, найденный на живой карточке** («Toronto FC – NYCFC» на «Матч ТВ HD» — матча там точно не было): `teamInTitle()` считал совпадением уже одно общее слово названия команды, а «FC» — токен и у `Toronto FC`, и у `New York City FC` — оказался ещё и токеном заголовка совершенно другой передачи, «⋗ Бокс. Bare Knuckle FC. Трансляция из США» (бокс, не футбол; «FC» здесь — часть названия лиги Bare Knuckle Fighting Championship). Оба «отличительных» токена команд не совпали никак («toronto»/«new york city» не встречаются в заголовке), но правило «достаточно одного слова» не отличало значимое слово от общего суффикса клубного имени — сработало на голом «fc» с обеих сторон разом. Исправлено точечно: `GENERIC_TEAM_TOKENS` в `epg.js` (`fc, cf, sc, afc, cfc, fk, ac, sk`) исключает из «одного слова достаточно» и из Левенштейн-цикла только короткие клубные аббревиатуры — они частые и вне футбола тоже, ноль опознавательной ценности сами по себе. Более длинные квалификаторы («United», «City», «Athletic», «Real») сознательно оставлены как есть: `Newcastle United` — контрпример, где «Ньюкасл» транслитерируется в «nyukasl» и не совпадает с «newcastle» даже по Левенштейну, так что реально матч находится только через «United»/«Юнайтед» (расстояние Левенштейна 2, укладывается в допуск) — расширять стоп-лист на такие слова нельзя, тут же ломает целый класс валидных совпадений. Проверено живьём: воспроизведено на реальном `guide.json` (ложная карточка исчезла, событий 59→57, чипов 96→94), плюс регрессия на 7 заведомо реальных парах команд (Tottenham–Everton, Real Madrid–Athletic Club и т.д. из Antifriz-проверки) — все по-прежнему находятся.

**Тот же класс бага, но без общего для всего футбола суффикса** — карточка «Cardiff City – Norwich City» (England EFL Cup) собрала 17 каналов трансляции: детские мультфильмы (`Big City Greens`, `LEGO City`), тревел-шоу (`City Breaks`), вообще не футбол. Оба клуба буквально называются «X City» — «city» не в `GENERIC_TEAM_TOKENS` (это не короткая аббревиатура вроде «fc», список нарочно её не трогает), поэтому засчитывалось «отличительным» словом для обеих сторон разом, и любой заголовок с голым «city» подряд удовлетворял и `home`, и `away` независимо друг от друга — «Ньюкасл»/«Реал» здесь ни при чём, слово было общим не с чужим заголовком, а с самим соперником по этой конкретной паре. Стоп-лист такое в принципе не может поймать (он глобальный, не знает про пары команд), поэтому фикс — не расширение списка, а новое правило: `meaningfulTeamTokens(teamTokens, opponentTokens)` вычисляется на каждую пару отдельно и вычитает из токенов команды всё, что есть и в токенах соперника (плюс `GENERIC_TEAM_TOKENS`, как раньше) — «city» выпадает из значимых токенов и для `Cardiff City`, и для `Norwich City` одновременно, остаются только `cardiff`/`norwich`. Если после вычитания у команды не остаётся вообще ни одного токена (вырожденный случай), фикс отступает на шаг назад — сперва пробует токены без учёта соперника, и только если совсем пусто — исходный список без фильтров, чтобы не отключить сопоставление полностью. Это заодно объясняет и Toronto FC/NYCFC другим способом: «fc» совпадает и у общего стоп-листа, и у соперника — оба механизма подстраховывают друг друга, а не дублируют один и тот же случай. Проверено живьём: `epg.findBroadcastChannels()` на реальном `guide.json` — 17 каналов → 1 (`ch3630`, настоящая трансляция), плюс регрессия на тех же 7 парах, что и раньше (включая `Newcastle United`/`West Ham United`, где «United» по-прежнему нужен и по-прежнему работает — общий токен теряется только когда соперник тоже его несёт).

### Известные слабые места (компромисс, не баг)

Транслитерация кириллицы — посимвольная (`normalize.js`), не официальная романизация: клубы с нестандартной англоязычной формой имени (сокращения вроде «ПСЖ» для Paris Saint-Germain) не совпадут вообще. Пока не встречалось на практике для проверенных турниров — калибровать по факту, если проявится.

Турнир в карточке — «Страна - Лига» как на самом FotMob (`json.details.country` + `json.details.name`), а не наше русское имя из `COMPETITIONS` (то теперь используется только для строки прогресса синхронизации, «Расписание: …»). Причина: у клубов имена приходят с FotMob как есть, по-английски — если лигу подписывать по-русски, а команды по-английски, на одной карточке получается разнобой языков. Имя страны — по короткому коду FotMob (`ENG`, `RUS`, `INT`…), не ISO-3166: маленькая захардкоженная таблица `COUNTRY_NAMES` в `fotmob.js`, тем же принципом, что и сам `COMPETITIONS`. `INT` (континентальные турниры типа Лиги чемпионов) — без префикса страны.

Список турниров в `COMPETITIONS` (`fotmob.js`) захардкожен, не в `config.json` — осознанно, под одного пользователя конфиг-опция не нужна. Пробовали и обратное: диалог «Турниры» с выбором из полного каталога FotMob (558 турниров, поиск, чекбоксы) — реализовали целиком и рабочим, но пользователь сразу забраковал вживую («слишком много ненужных турниров», «фича пока не нужна») и попросил убрать. Убран полностью: `fotmob.js` → `allLeagues()`, IPC `competitions:list/get/save`, кнопка и диалог в `index.html`/`app.js`/`styles.css` — ничего не осталось даже мёртвым кодом. Если понадобится снова — эндпоинт `https://www.fotmob.com/api/data/allLeagues` (94 страны + international, `{id, name, ccode}` на турнир) уже разведан и проверен живьём, начинать пришлось бы не с нуля.

Названия в `COMPETITIONS` — английские, как у самого FotMob (`details.name`), не перевод на русский: пользователь попросил явно, заодно это совпадает с тем, что уже показывает карточка матча (та берёт `details.name`/`details.country` напрямую, см. ниже) — раньше по-русски было только это поле, использовавшееся исключительно для строки прогресса синхронизации.

Кубки/суперкубки в дефолтном списке — только для топ-5 лиг (Англия/Испания/Италия/Германия/Франция) и России, по прямой просьбе пользователя. Кубки Нидерландов, Бельгии, Португалии, Турции, Бразилии и Аргентины убраны — их лиги при этом остались. Континентальные турниры (Лига чемпионов/Европы/конференций + квалификации, Кубок Либертадорес) под это правило не подпадают — не привязаны к одной стране. Беларусь (лига + кубок) убрана целиком отдельным решением, тоже по просьбе пользователя, до этого была добавлена в рамках «Бразилия, Аргентина, Беларусь — главная лига + кубок» — то решение частично отменено. Добавлены Премьершип Шотландии (`id 64`) и 2. Бундеслига Германии (`id 146`) — единственные два турнира из присланного пользователем списка (топ-лиги + Ла Лига/Серия А/Бундеслига/Лига 1/ЛЧ/ЛЕ + горстка кубков/MLS/Эредивизи/Португалия/РПЛ/Бельгия), которых раньше не было; остальные 17 уже присутствовали.

Карточка матча слегка подсвечена цветом турнира: FotMob отдаёт свой официальный брендовый цвет прямо в ответе (`json.details.leagueColor`, есть у всех проверенных турниров, даже у самых мелких — просто нейтральный тёмно-серый `#333333`, если своего цвета нет) — прокинут как `competitionColor`/`tournamentColor` до `renderer/app.js`, там ставится инлайновой CSS-переменной `--accent` на карточку. В `styles.css` красит только левую полоску рамки (`border-left-color`) и лёгкую диагональную заливку фона через `color-mix()` — сознательно по минимуму, после нескольких неудачных попыток (полноразмерный полупрозрачный герб-«водяной знак» в углу карточки читался плохо для тёмных гербов вроде АПЛ, потом пробовали однотонный силуэт через `mask-image` — тоже не понравилось пользователю визуально) в итоге просто убрали водяной знак совсем, оставив только рамку и заливку. Для матчей «в эфире» (`.is-live`) подсветка live-статуса красит рамку только с трёх сторон (не через `border-color` целиком) — иначе цвет турнира на левой стороне забивался бы одинаковым оранжевым у всех live-карточек разом, и они переставали отличаться друг от друга.

**Живая минута матча** (`event.clock`) — эндпоинт `leagues?id=` сам по себе её не отдаёт (только `started`/`finished`/итоговый счёт), но после списка турниров `fotmob.js` → `fixtures()` берёт из уже построенного списка только фикстуры со `status === 'inprogress'` (обычно 1–3 разом, не сотни) и точечно дёргает `matchDetails?matchId=` для каждой. Минута — `json.header.status.liveTime.short` (не `json.general.status`, там `liveTime` нет вообще — на этом споткнулись при разведке: `general.status` просто `undefined`, значение через `||`-фолбэк тогда случайно бралось из `header.status`, из-за чего сперва казалось, что рабочее поле — `general`). Значение вида `"67‎'‎"` — с невидимыми directional-mark символами вокруг апострофа, обёрнутыми вокруг цифр — очищается регэкспом до голых цифр (+ «+N» для добавленного времени) и своего апострофа.

Обновляется вместе со счётом и статусом — раз в 3 минуты, но отдельным от полного синка циклом (`sync.js` → `refreshScores()`, см. «Два цикла обновления» ниже), не вместе с пересборкой всего расписания.

Стадион (`event.venue`) через `matchDetails` не запрашивается — тот же принцип, что и раньше (венью нужен был бы такой же отдельный запрос ради небольшой пользы), строка стадиона просто не выводится, рендерер это обрабатывает штатно.

## Два цикла обновления: расписание отдельно от счёта

Раньше был один цикл на всё — каждые 3 минуты (и по кнопке «Обновить») `sync.run()` пересобирал вообще всё: заново дёргал все ~55 турниров у FotMob, заново качал/парсил EPG (хоть и с 6-часовым диском-кэшем самого файла), заново гонял сопоставление команд с каналами по всем ~16–46 тысячам передач. Расписание и список каналов меняются медленно — пересобирать их каждые 3 минуты не было смысла, а вот счёт/статус/минута у уже найденных матчей за 3 минуты успевают устареть. Пользователь попросил развести это на два независимых цикла.

**Полный синк** (`sync.js` → `run()`, IPC `guide:sync`, кнопка «Обновить») — без изменений по сути, просто реже: при запуске приложения, раз в час (`setInterval` в `app.js`) и по клику — качает все турниры, всю EPG, пересчитывает сопоставление с нуля, пишет `guide.json` целиком.

**Лёгкое обновление счёта** (`sync.js` → `refreshScores()`, IPC `guide:refreshScores`) — раз в 3 минуты, тем же интервалом, что раньше был у полного синка, но теперь отдельным вызовом. Не трогает FotMob-турниры списком и не трогает EPG вообще — берёт уже готовый `guide.json`, отбирает события, у которых `start <= now` и `status !== 'finished'` (то есть уже начавшиеся и ещё не завершённые — как правило это ровно те же 1–5 матчей, что и «живые» для минуты), и для каждого точечно дёргает `matchDetails?matchId=` (`fotmob.js` → `matchStatus()`, который заменил собой более узкую `liveClock()` — тот же эндпоинт, просто теперь отдаёт статус/счёт/минуту разом, а не только минуту). У матча, который ещё не начался (`start > now`), при таком отборе нет вообще никакого сетевого запроса — его `start` уже говорит всё, что нужно знать, до самого удара по мячу.

Матч, ставший `finished` во время лёгкого обновления, **удаляется из гида** тем же проходом (то же правило «только живое и предстоящее», что и в `run()`), а не ждёт следующего полного синка — иначе он бы зависал в списке лишний час. `guide.generatedAt` при лёгком обновлении не трогается — оно означает «последний полный синк расписания», а не «последнее любое изменение»; статус-строка в интерфейсе тоже не обновляется на каждый тик (`renderer/app.js` → `doScoreRefresh()` работает тихо, без сообщений и без блокировки кнопки «Обновить» — виден только результат: тикающий счёт, появляющийся бейдж LIVE, пропадающая завершённая карточка).

Проверено живьём (`sync.refreshScores()` напрямую): матч, который на деле оказался `finished`, корректно выпадает из гида целиком вместе с турниром, если это был единственный матч в нём; матч с `start` в будущем не трогается ни разу, ни одного лишнего запроса.

## Плеер: VLC вместо hls.js

`hls.js` не смог воспроизвести часть потоков (interlaced 1080i H.264 — `mux.js` зависает при перемультиплексировании в fMP4 для MSE, без единой ошибки, просто чёрный экран). VLC тот же поток играет нормально (нативный декодер, не через MSE браузера) — проверено вживую. Пользователь предпочёл полностью заменить встроенный плеер на VLC вместо разбора, у каких потоков конкретно проблема.

### От докинга — к двум независимым окнам

Первая версия «пришвартовывала» окно VLC поверх видео-области внутри окна приложения: снимала рамку/заголовок, непрерывно синхронизировала размер и позицию через `SetWindowPos` при каждом ресайзе/перемещении/фокусе. Работало, но тянуло за собой целый хвост Win32-грабель (см. ниже) и, несмотря на все фиксы, при переключении канала часть экрана оставалась чёрной, пока пользователь не кликал по ней вручную мышью — Direct3D-поверхность VLC не откликается на программную GDI-перерисовку (`RedrawWindow`), только на реальный клик, а разбираться, как синтетически воспроизвести именно то, что делает клик, оказалось сложнее и хрупче, чем просто отказаться от докинга.

Пользователь попросил вместо этого развернуть интерфейс иначе: окно приложения — только лента матчей (`electron/main.js` → `createWindow()`), шириной `GUIDE_WIDTH = 440`, прижатая к левому краю экрана на всю высоту рабочей области. VLC теперь открывается как полностью независимое окно ОС — свой заголовок, свои элементы управления, пользователь двигает/ресайзит/разворачивает его сам. Это заодно устранило и баг с чёрным экраном: он был следствием скрытия/срезания рамки при докинге, а не общей проблемой VLC.

**Как устроено сейчас:** `electron/vlc.js` — запускает `vlc.exe` как отдельный процесс на URL потока, через Win32 (`koffi`, без компиляции) находит его окно по PID (`EnumWindows`+`GetWindowThreadProcessId`) и **один раз**, при первом запуске, ставит его рядом с окном приложения (`SetWindowPos`) — без снятия рамки, без непрерывного слежения. `electron/main.js` → `vlcTargetBounds()` считает это место как «всё, что осталось от рабочей области дисплея за вычетом ширины окна приложения», пересчитывается заново при каждом клике «play», но применяется только если VLC ещё не запущен (`current === null` в `vlc.js`) — иначе окно уже принадлежит пользователю, трогать его не надо.

Переключение канала при уже запущенном VLC — это просто смена URL через его собственный HTTP-интерфейс управления (`pl_empty`+`in_play`), без пересоздания и без перепозиционирования окна.

### Грабли, вживую найденные при подключении VLC

Актуальны и для текущей модели (без докинга) — они про сам процесс/CLI VLC, а не про синхронизацию окна.

**`--play-and-exit=no` — невалидный синтаксис.** VLC не принимает `=no`/`=yes` для булевых флагов, только `--no-play-and-exit`. С неверным флагом VLC падал на старте ещё до открытия окна — процесс появлялся и тут же исчезал, выглядело как «зависание», а на деле `vlc: unknown option` в stderr.

**VLC разворачивается на весь экран уже ПОСЛЕ старта воспроизведения**, а не при создании окна — судя по всему, из-за личных настроек VLC пользователя (сохранённое «включить на весь экран» в его `vlcrc`). `--no-fullscreen` и `--no-qt-video-autoresize` не помогли перебить это сами по себе. `SetWindowPos` при этом каждый раз возвращал `true` (успех), но реальная геометрия окна оставалась (0,0,ширина_монитора,высота_монитора) — признак того, что окно в состоянии `WS_MAXIMIZE`, для которого Windows игнорирует размер/позицию из `SetWindowPos`, пока не восстановить его явно.

**Фикс — двухчастный:** (1) `ShowWindow(hwnd, SW_RESTORE)` непосредственно перед каждым `SetWindowPos`, снимает maximized-состояние; (2) этого мало на один раз — VLC переразворачивается через ~1 секунду после старта декодирования, так что позиционирование переустанавливается ещё несколько раз в первые ~3.5 секунды сразу после запуска (`play()` → цикл `setTimeout` на 300/700/1200/2000/3500 мс), пока не «устаканится». После этого окно уже никто не трогает — оно в полном распоряжении пользователя.

**Моргание окна при переключении канала (актуально и сейчас).** Изначально `play()` каждый раз убивал старый процесс VLC и поднимал новый — пересоздание окна ОС и было причиной моргания. Фикс: VLC запускается с `--extraintf=http --http-port=... --http-password=...` (loopback, случайный пароль на процесс), при живом `current` `play()` просто шлёт `pl_empty`+`in_play` через это HTTP-API вместо перезапуска процесса.

## Устройство

```
electron/
  main.js        окно ленты матчей (прижато к левому краю экрана), IPC, диалог «Источники»
  paths.js       пути: в разработке — папка проекта, в сборке — %APPDATA%\iptv-match-center
  playlist.js    парсер M3U, источник — файл или URL
  normalize.js   канонизация имён (рус→лат, отбрасывание маркеров качества) — для каналов и для команд
  fotmob.js      расписание/счёт/статус с FotMob (без ключа) для списка турниров
  epg.js         скачивание/кэш XMLTV, поиск каналов под уже известный матч
  sync.js        FotMob + EPG → guide.json (полный синк + лёгкое обновление счёта)
  vlc.js         запуск VLC отдельным окном ОС рядом с окном приложения (Win32 через koffi)
  store.js       JSON-кэш на диске
renderer/        index.html, app.js, styles.css — только лента матчей, плеер полностью снаружи (VLC)
scripts/         epg-probe (разведка формата фида)
```

`config.json` в корне репозитория — личный рабочий конфиг пользователя (реальные пути плейлиста/EPG), в git не попадает (см. «Безопасность»). Закоммичен только пустой шаблон `config.example.json` — его же теперь пакует `electron-builder` (`build.files` в `package.json`) и с него же стартует `ensureConfig()` при первом запуске что в dev, что в упакованной сборке. Раньше `config.json` паковался как есть, поэтому перед каждым `npm run dist` его приходилось вручную зануля́ть и восстанавливать после — с шаблоном это больше не нужно.

Зависимости: `electron` и `koffi` (нативный биндинг для Win32-вызовов — единственное исключение из «нет нативных модулей», обосновано в разделе про VLC). `hls.js` удалён вместе со встроенным плеером. База данных не нужна — кэш лежит JSON-файлами.

## Плейлист и EPG — раздельные источники, диалог «Источники»

Раньше плейлист выбирался только файлом (диалог ОС), а EPG — только неявно, через `url-tvg` внутри самого плейлиста (оверрайд был, но только правкой `config.json` руками). Пользователь попросил разделить: у плейлиста и EPG теперь независимые поля, и оба могут быть либо локальным файлом, либо прямой ссылкой.

`electron/playlist.js`: `parse(path)` (только файл) заменён на `parseText(text)` (чистый разбор строки, без источника) + `load(source)` (async; `source` — файл или `http(s)://`-ссылка, определяется `isUrl()`). Для URL — обычный `fetch` (не `electron.net.fetch`): это ссылка из собственной подписки пользователя у своего же IPTV-провайдера, а не публичный API с защитой от ботов, так что спецстек Chromium тут не нужен — тот же выбор, что уже был сделан для EPG-фида в `epg.js`. Кэша на диске для плейлиста нет (в отличие от EPG-фида, который весит 30–170 МБ) — и раньше локальный файл перечитывался с нуля при каждой синхронизации, свежий фетч по URL — та же по цене операция, не новая.

`electron/paths.js` → `resolvePlaylist()` пропускает `http(s)://`-строки как есть, не пытаясь склеить их с `dataDir` как путь.

IPC: `sources:get`/`sources:save` — новая пара, отдаёт/сохраняет `{playlistPath, epgUrl}` разом; `playlist:choose` остался, но теперь просто открывает диалог выбора файла и возвращает путь, без побочного сохранения в конфиг — сохранение теперь всегда через `sources:save`, единой точкой.

## Путь к vlc.exe — тоже в диалоге «Источники»

`vlcPath` раньше можно было переопределить только правкой `config.json` руками (см. `vlc.js` → `findVlcPath()` — без оверрайда перебирает пару стандартных путей `Program Files`). Первая попытка добавила для этого отдельный диалог «Настройки» — пользователь сразу попросил объединить обратно с «Источниками» в одну точку входа, не плодить диалоги ради одного поля. Итог: третье поле в том же `sourcesDialog`, тот же паттерн, что у выбора плейлиста — IPC `vlc:choose` (диалог выбора файла, фильтр `.exe`, без побочного сохранения), сам путь уходит и приходит вместе с `playlistPath`/`epgUrl` через `sources:get`/`sources:save`. `sources:save` проверяет `fs.existsSync()` для `vlcPath` перед записью (в отличие от `playlistPath`, это поле необязательное — пустая строка не ошибка, а сброс к автоопределению, ключ не пишется в JSON).

## Работа с любым провайдером плейлиста/EPG

Изначально всё (парсинг группы, отбор «спортивных» каналов, таблица группа→страна) было откалибровано под одного конкретного провайдера. Пользователь явно попросил научиться работать с чужими плейлистами тоже — проверено на живом примере другого провайдера (Antifriz, `#EXTM3U ... url-tvg="http://tchaikovsky.af-stream.com:8080/epg.xml.gz"`, `tvg-id="nash-futbol-hd-orig"` — заметно другой стиль id, чем числовые `chNNNN` у текущего). Сделано три вещи:

1. **Группа канала** — раньше бралась только из отдельной строки `#EXTGRP:` (особенность текущего провайдера). Теперь `playlist.js` сперва читает стандартный атрибут `group-title=""` прямо в `#EXTINF` (то, что понимают «обычные» плееры/парсеры), а `#EXTGRP:`, если он тоже есть, просто переопределяет — так у текущего провайдера ничего не поменялось (у него `group-title` нет вообще), а у провайдеров со стандартным M3U это заработало.
2. **Отбор «это матч или нет» — без привязки к «спортивным» каналам вообще**, см. `epg.js` → `programmes()` выше: раньше был обязательный предфильтр по группе/имени, откалиброванный под текущего провайдера («9. Sport/Спорт» с номером) и ломавшийся на другом стиле («Спорт» без номера у Antifriz). Убран целиком — сканируются все каналы, что есть в плейлисте, а не только «похожие на спортивные».
3. **Формат EPG-фида по содержимому, не по URL** — `epg.js` → `loadXmltv()` понимает как есть: обычный `.xml`, `.xml.gz`, и `.xml.tar.gz` (gzip-сжатый tar с одним XML-файлом внутри — без библиотеки, свой мини-`untar()` на 512-байтные заголовки, достаточно для «достать один файл из одного архива»). Определяется по магическим байтам после распаковки (ведущий `<` — это XML, иначе распаковывается как tar), а не по расширению в ссылке — так что неважно, какой конкретно вариант отдаёт провайдер.

**Что осталось провайдер-специфичным осознанно** (не блокирует основной сценарий, деградирует тихо): таблица «номер группы → страна» (`GROUP_COUNTRY` в `playlist.js`) — она нужна только для маленького флажка-страны на чипе канала; для незнакомой схемы групп страна просто останется `null` (чип без флажка), это не мешает найти и воспроизвести трансляцию. Префикс имени вида `UK:`/`IT:` — уже достаточно общий паттерн, отдельной калибровки не потребовал.

**Баг, найденный именно на живом переключении между провайдерами**: `epg.js` кэшировал скачанный XMLTV-фид под фиксированным именем файла `epg.xml.gz` (TTL 6 часов), без привязки к URL. При смене EPG в «Источниках» (например, с постоянного провайдера на Antifriz) `loadXmltv()` видел ещё не устаревший файл на диске и тихо отдавал **старый** фид — с чужой схемой `channel id`, которая не пересекается ни с одним `tvg-id` нового плейлиста. Ни одной ошибки при этом не бросалось: `sync.js` просто не находит трансляций и пишет пустой `guide.json` — с виду выглядит как «плейлист не работает», хотя на деле весь конвейер (парсинг, разбор EPG, сопоставление команд) в полном порядке — так и оказалось при живой проверке: собранный вручную конвейер на присланном фрагменте плейлиста Antifriz находил все трансляции корректно, а через реальное приложение сетка была пустой именно из-за протухшего-не-по-времени, а не-по-адресу кэша. Поймано на реальном сравнении: `cache/epg.xml.gz` (17.9 МБ, от предыдущего провайдера) лежал рядом с `guide.json` весом 187 байт (пустая сетка) — при том что фид, реально отвечающий по новому `url-tvg`, содержал тысячи актуальных передач. Исправлено: имя файла кэша теперь `epg-{sha1(url)}.xml.gz` — разные EPG-адреса кэшируются раздельно, старый провайдер не может подмешаться к новому. Старый `cache/epg.xml.gz` больше не используется никаким кодом — просто осиротевший файл, можно спокойно удалить вручную, само приложение его не трогает.

## Особенности плейлиста этого провайдера

Один и тот же канал присутствует в нескольких вариантах качества плюс зеркала `Double`. Ранг считает `quality()` в `playlist.js`: `+N` в имени — это сдвиг по времени, а не живой эфир, он штрафуется сильнее всего.

## Архивные ссылки («С начала матча») — пробовали и убрали целиком

Формат архивной ссылки провайдер нигде не сообщает (в плейлисте есть `tvg-rec="7"`, но не `catchup-source`) — был `npm run probe-catchup -- <tvg-id>`, перебирал восемь известных схем (Flussonic `index-{start}-{dur}.m3u8` и т.п.) и печатал рабочую. Кнопка «С начала матча» в интерфейсе была реализована, но по просьбе пользователя убрана — а раз кнопки нет, весь механизм под ней (`scripts/probe-catchup.mjs`, IPC `stream:catchup` в `main.js`, `catchupUrl` в `preload.js`, `timeshiftDays` у канала в `playlist.js`/`sync.js`) удалён целиком, а не оставлен висеть неиспользуемым. Если понадобится опять — тот же путь: `probe-catchup` находил рабочую схему для тестового `ch695` живым перебором, начинать пришлось бы с той же разведки заново.

**Потоки переехали** с `index.m3u8` на `mono.m3u8` между двумя версиями плейлиста — на воспроизведение не влияет, только историческая заметка теперь (архивные ссылки, на которые это влияло, больше не строятся).

## Грабли, на которые уже наступали

`Sec-Fetch-*`, `Origin` и `X-Requested-With` — запрещённые имена заголовков. Chromium выставляет их сам и бросает исключение при попытке задать вручную. Выглядит как сетевая ошибка.

Атрибут `hidden` перебивается любым правилом вида `.bar { display: flex }`. В `styles.css` для этого стоит `[hidden] { display: none !important; }` — не удалять.

На Windows GUI-процесс Electron ненадёжно печатает в родительскую консоль, поэтому все диагностические скрипты дублируют вывод в `*.log` рядом с `package.json`.

VPN ломает всё: Cloudflare режет датацентровые диапазоны. Если внешние запросы вдруг отдают 403 на всё подряд — первым делом проверить туннель.

Если `ELECTRON_RUN_AS_NODE=1` стоит в окружении, `electron.exe` запускается как обычный Node — `require('electron')` возвращает путь строкой вместо модуля, и `app.isPackaged` в `paths.js` падает с `TypeError: Cannot read properties of undefined`. Перед обычным запуском (`electron .`) убедиться, что переменная снята (`Remove-Item Env:\ELECTRON_RUN_AS_NODE` в PowerShell) — она же, наоборот, нужна, если хочешь прогнать какой-то `.js`-файл через связанный с проектом Node без `npm`/`node` в PATH.

(Sofascore-специфичное: расписание за соседние даты перекрывалось, события у полуночи приходили дважды — решалось дедупликацией по `id`. У EPG-конвейера дублей такого рода нет: `sync.js` берёт даты прямо из `event.start` вместо запроса по окну дат, а показы одного матча на разных каналах и так сводятся в одну карточку — `epg.findBroadcastChannels()` сама возвращает список всех подходящих `channelId` для одной фикстуры.)

## Стиль

Пользователь предпочитает минимальные решения и возражает против переусложнения. Не добавлять зависимости без необходимости, не вводить базу данных, не плодить слои абстракции. Отвечать по-русски.

## Безопасность

`playlist.m3u8` содержит токен доступа в URL каждого канала. Файл в `.gitignore` — не коммитить, не показывать в выводе целиком.

`config.json` тоже в `.gitignore` — хранит личный путь к плейлисту пользователя (и, потенциально, EPG-ссылку с чувствительными параметрами). В git — только пустой шаблон `config.example.json`.
