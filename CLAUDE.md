# CLAUDE.md

Рабочие заметки по проекту. Читай перед тем, как что-то менять.

Здесь — как всё устроено сейчас и обо что можно споткнуться. Разборы уже
принятых решений и уже провалившихся экспериментов вынесены в
[DECISIONS.md](DECISIONS.md): туда стоит заглянуть, прежде чем предлагать
второй источник расписания, второй EPG-фид, встраивание плеера в окно или
замену транслитерации на внешний справочник имён — всё это уже пробовали, и
там записано, чем кончилось.

## Что это

Electron-приложение: спортивная телепрограмма поверх IPTV-плейлиста. Окно приложения — только лента матчей по турнирам с кнопками каналов, прижатая к левому краю экрана; VLC играет поток в своём отдельном, независимом окне ОС рядом (не встроен и не «пришвартован» — см. «Плеер: VLC вместо hls.js» ниже; история, почему не встроен, — в DECISIONS.md). Русский интерфейс, пользователь — один, дистрибутив под Windows.

Запуск: `npm start`. Сборка: `npm run dist`.

## Текущее состояние: расписание из FotMob, каналы — через сопоставление с EPG

Предыдущие три версии (Sofascore, слепой разбор заголовков EPG, ESPN) и
живая проверка всех рассмотренных источников — Sofascore, TheSportsDB,
API-Football, football-data.org, WhoScored, sports.ru, ESPN — разобраны в
[DECISIONS.md](DECISIONS.md). Коротко: FotMob выбран потому, что не требует
ключа и аккаунта и покрывает кубки и низшие дивизионы, которых нет у ESPN.

**Текущая модель:** `electron/fotmob.js` тянет расписание/счёт/статус с публичного JSON-API FotMob (`www.fotmob.com/api/data/...`, без ключа и аккаунта) для фиксированного списка турниров; `electron/epg.js` только ищет, на каких каналах плейлиста идёт уже известный матч (по времени + именам команд), парсинг заголовков «вслепую» не нужен.

Лиги: АПЛ, Чемпионшип (Англия, 2-й дивизион), Ла Лига, Серия A, Бундеслига, Лига 1, Лига чемпионов, Лига Европы, Лига конференций, Примейра-лига (Португалия), Эредивизи (Нидерланды), Про-лига (Бельгия), РПЛ, Суперлига (Турция), MLS.

Кубки/суперкубки: Кубок и Суперкубок Англии (Community Shield), Кубок английской лиги (EFL/Carabao Cup), Кубок и Суперкубок Испании, Кубок и Суперкубок Италии, Кубок и Суперкубок Германии, Кубок и Суперкубок Франции, Кубок Нидерландов, Кубок и Суперкубок Бельгии, Кубок и Суперкубок Португалии, Кубок и Суперкубок Турции — все девять пар, которых не было в ESPN, теперь на месте.

**Россия — все турниры, что знает FotMob**, не только РПЛ + Кубок (явная просьба пользователя): РПЛ, Кубок России, Суперкубок России, Первая лига (ФНЛ), Стыковые матчи РПЛ (плей-офф РПЛ↔ФНЛ), Вторая лига (3-й дивизион) — последняя позже убрана отдельным явным запросом, остальной набор остался.

Бразилия, Аргентина, Беларусь — только главная лига + главный кубок каждой (не «все турниры», как у России — так не просили): Серия A + Кубок Бразилии, Лига Профессионал + Кубок Аргентины, Премьер-лига + Кубок Беларуси.

**Квалификации ЛЧ/ЛЕ/ЛК — отдельные турниры на FotMob**, не то же самое, что «Лига чемпионов»/«Лига Европы»/«Лига конференций» с других id. У основных турниров основной этап начинается позже (сентябрь), и на момент добавления они всё ещё стояли на прошлом сезоне (`selectedSeason` у FotMob не обновился) — расписание было пустым, из-за чего показалось, что еврокубков нет вообще, хотя вся текущая активность (плей-офф квалификации) шла именно в отдельных Qualification-турнирах (id `10611`/`10613`/`10615`), которых в `COMPETITIONS` не было. Плюс Кубок Либертадорес (`id: 45`, сезон по календарю South America, `selectedSeason: "2026"`) — отдельной квалификации под него на FotMob нет (в отличие от УЕФА), ранние раунды идут в том же id.

**Баг попутно найден и исправлен**: `COUNTRY_NAMES[code] ?? code ?? null` не отличал «код замаплен на `null` осознанно» (INT — без префикса страны) от «кода вообще нет в таблице» — `??` реагирует на `null`/`undefined` одинаково в обоих случаях. Карточки еврокубков показывали «INT - Champions League Qualification» вместо просто «Champions League Qualification». Баг существовал с самого появления фичи «Страна - Лига», просто не проявлялся: у ЛЧ/ЛЕ (`id 42`/`73`) в окне синка ни разу не было матчей до сегодняшних квалификаций. Исправлено явной проверкой `code in COUNTRY_NAMES` вместо `??`.

Полный список id проверен живьём по `https://www.fotmob.com/api/data/allLeagues` перед добавлением — то же правило, что было при подборе слагов ESPN: не гадать, всегда сверяться с реальным ответом.

У Италии два разных id с похожими именами — `222` («Super Cup») и `11015` («Supercoppa Italiana») — на деле первый мужской (Napoli/Milan/Bologna/Inter в реальных матчах), второй женский. В `COMPETITIONS` используется `222`.

### Как устроено сейчас

`electron/fotmob.js` — `fixtures(daysBack, daysForward, onProgress)` дёргает `www.fotmob.com/api/data/leagues?id={id}` на каждый турнир из `COMPETITIONS` и берёт `fixtures.allMatches` (fallback на `overview.matches.allMatches`, оба поля видел на разных турнирах с одинаковым содержимым). В отличие от ESPN здесь нет параметра диапазона дат — эндпоинт всегда отдаёт весь текущий сезон целиком, окно `[сегодня-daysBack, сегодня+daysForward]` применяется на своей стороне, после разбора ответа. Логотипы команд/лиг — не отдельный запрос, а детерминированный статический путь: `images.fotmob.com/image_resources/logo/{teamlogo|leaguelogo}/{id}.png` (проверено живьём, включая герб РПЛ — актуальный, никакого оверрайда вроде того, что был нужен для ESPN, не потребовалось). Работает только через `electron.net.fetch` (стек Chromium) — обычный `fetch`/`Invoke-WebRequest` с этого же хоста тоже блокируется (тот же класс защиты, что у Sofascore/TheSportsDB).

`electron/epg.js` не менялся под эту миграцию:
- `loadXmltv(url)` — скачивание + дисковый кэш на 6 часов, путь через `store.root`. Возвращает **Buffer, а не строку** — намеренно, см. `programmes()` ниже. Обрыв закачки — по простою (45 с без единого байта), а не по общему времени: фид весит десятки мегабайт, и таймаут на всю операцию был бы отсечкой по скорости, а не защитой от зависания.
- `programmes(xmlText, channels)` — плоский список передач на **всех** каналах, что есть в плейлисте (`channelId, title, start`), отсортированный по времени, без попытки понять из заголовка, что это за матч. Раньше отбирал только «спортивные» каналы по эвристике (номер группы `9.`/имя группы или канала со словом sport/спорт) — убрано целиком по просьбе пользователя: эвристика была откалибрована под одного провайдера (у другого, например Antifriz, спортивная группа называется просто «Спорт» без номера) и всё равно пропускала матчи на нейтральных каналах (сборная на Первом, Кубок Германии на ARD — ни то, ни другое не назвать «спортивным» ни по имени, ни по группе). Реальный отбор «это матч или нет» и так делает `findBroadcastChannels()` ниже — сканировать все каналы дороже по CPU, но на живом прогоне (3962 канала вместо 668, ~217k передач вместо ~46k) время синка не изменилось заметно, а трансляций находится больше (было 97, стало 122 на одном и том же плейлисте).
- `findBroadcastChannels(progList, home, away, kickoffMs)` — для уже известного матча ищет передачи в окне ±90 минут от начала, где заголовок называет **обе** команды (через `normalize.tokens()`/`similarity()` — то же, что раньше матчило имена каналов). Достаточно совпадения «отличительного» слова названия команды, не всех токенов сразу — см. ниже почему.
- **Память: разбор идёт по БАЙТАМ, и это принципиально.** Фид — 180 МБ, около 150 миллионов символов; из-за кириллицы V8 держит строку по два байта на символ, то есть создание одной такой строки стоит четверть гигабайта. Поэтому `loadXmltv()` отдаёт Buffer, а `programmes()` ищет границы `<programme>` через `buf.indexOf` и превращает в JS-строки только мелкие куски — атрибуты открывающего тега и тело тех передач, что прошли отбор. Второе: `programmes()` принимает время начала известных матчей и **выбрасывает всё вне окон ±90 минут вокруг них** — матчер туда всё равно не заглядывает ни разу, а это 73% фида. Фикстуры известны до загрузки EPG, так что фильтр применим прямо при разборе. Вместе: **память после синка 514 → 172 МБ** при побайтово одинаковом результате (83 матча, 274 трансляции; разбор сверен по всем 358 835 передачам — ноль расхождений). Байтовый разбор чуть медленнее строкового (1.5 с против 1.3 с) — это осознанный размен.
  **Грабли измерения**: `gunzipSync` и цикл разбора блокируют event loop, поэтому замер пика через `setInterval` их просто не видит и врёт в разы. Мерить только синхронными контрольными точками.
- **Стоимость этого шага и что с ней сделано.** Матчинг — самая дорогая часть синка, не сеть: на живом фиде (306k передач) он занимал 5 секунд против 1 секунды на разбор XML. Две причины, обе устранены без изменения результата (сверено по каждому матчу с прежней версией — ноль расхождений): (1) окно вокруг свистка искалось проходом всего списка с головы для **каждого** матча — теперь бинарный поиск (`firstAtOrAfter`, список и так отсортирован); (2) `tokens(p.title)` считался заново на каждую пару (матч, передача) — 208 тысяч вызовов там, где различных передач в окнах всего 69 тысяч; теперь токены и признак кириллицы запоминаются на самой передаче по первому обращению (`titleTokens`/`titleIsCyrillic`). Именно **лениво**, а не заранее в `programmes()`: заранее пришлось бы токенизировать весь фид (136 тысяч различных заголовков), а рядом со свистками лежит вдвое меньше. Этап EPG в сумме 6.1 → 4.6 с. Та же болезнь была в `sync.js` у проверки «что EPG показывает на этом канале» — она фильтровала весь `progList` на каждую заявку вещателя, теперь есть индекс по `channelId`.

`electron/sync.js`: `fotmob.fixtures()` → для каждой фикстуры `epg.findBroadcastChannels()` → `guide.json`. Форма — плоский `events`, отсортированный по времени начала (`{ generatedAt, channelCount, stats, events }`). До 1.4 здесь строилось дерево `days → tournaments → events`, унаследованное ещё от `espn.js`, но рендерер тут же расплющивал его обратно: заголовков дня и турнира в интерфейсе нет, `day.date` и `tournament.name` не читались нигде, а `refreshScores()` был вынужден обходить и переупаковывать все три уровня. Кэш старой формы не мигрируется — `main.js` → `cachedGuide()` считает его отсутствующим, полный синк при запуске всё равно перезапишет файл. Окно расписания — вчера + 6 дней вперёд (`DAYS_BACK`/`DAYS_FORWARD` в `sync.js`); дальше EPG-фид всё равно не заглядывает (~4–5 дней вперёд), так что у поздних фикстур `broadcasts` пока пустой — это нормально, не баг.

Полный прогон (37 турниров, ~16 секунд, живой плейлист) не дал ни одной ошибки; ФНЛ и найденные ранее недостающие кубки уже строят карточки с трансляциями.

### Правила сопоставления команд, действующие сейчас

Каждое правило родилось из живого ложного срабатывания на реальной карточке.
Разбор каждого случая, с числами и именами каналов, — в
[DECISIONS.md](DECISIONS.md); здесь только то, что действует.

- **Достаточно одного «отличительного» слова** названия команды, не всех
  токенов сразу. Город транслитерируется непредсказуемо («Москва» →
  `moskva`, а не `moscow`), и требование полного совпадения обнуляло всю
  РПЛ целиком.
- **`GENERIC_TEAM_TOKENS`** — короткие клубные аббревиатуры (`fc`, `cf`,
  `sc`, `afc`, `cfc`, `fk`, `ac`, `sk`) плюс `wanderers` и `west`. Это
  слова, которые сами по себе клуб не опознают и встречаются вне футбола.
  Длинные квалификаторы («United», «City», «Athletic», «Real») сюда
  намеренно НЕ входят: без них ломается целый класс валидных совпадений
  («Ньюкасл» до `newcastle` не дотягивается, спасает только «Юнайтед»).
- **`meaningfulTeamTokens()`** вычитает из токенов команды всё, что есть и у
  соперника по этой же паре. Иначе «Cardiff City» против «Norwich City»
  удовлетворяются любым заголовком с голым «city» — обе стороны разом.
  Коллизию с ТРЕТЬИМ, посторонним матчем это по конструкции не ловит — для
  таких слов есть глобальный список выше.
- **Нечёткая ветка (Левенштейн) существует только ради шума
  транслитерации.** Допуск плавающий, `floor(длина/3)`, и только для слов
  длиной ≥ 5. Для заголовка, уже написанного латиницей, ветка сужена до слов
  ТОЙ ЖЕ длины: там расхождение бывает максимум в диакритике, а это замена
  символа, длину не меняющая.
- **Три формы имени** с каждой стороны: полное, короткое от FotMob
  (`homeShort`/`awayShort`) и запись из `RU_NICKNAMES` — маленький
  курируемый словарь клубов, до которых транслитерация не дотягивается
  вовсе. Пул токенов соперника для вычитания строится сразу из всех форм.
- Окно поиска — ±90 минут от стартового свистка (`WINDOW_MS` в `epg.js`,
  `sync.js` берёт оттуда же).

Все правила закреплены тестами. **Трогая любое из них, сперва посмотри,
какой кейс оно держит** — `npm test` покажет это быстрее, чем чтение
разбора.

## Второй источник трансляций: «где смотреть» от FotMob

`electron/broadcasters.js` дёргает недокументированный
`tvlistings?matchId=1&countryCode=XX` — список вещателей по одной стране.
Ключ ответа — уже наш собственный id матча от FotMob, так что сопоставления
имён команд не нужно вовсе. Закрывает класс случаев, который EPG-путь не
решает в принципе: у британских Sky Sports в заголовках передач названий
команд нет физически, там брендированные слоты вида «Saturday Night
Football». Список стран — не хардкод, а реальный набор `channel.country`
из плейлиста; запросы батчатся по 8 — общая для всех обращений к этому хосту
величина, `BATCH_SIZE` в `net.js`. Раньше она стояла тремя копиями с
перекрёстными комментариями «та же величина, что в соседнем файле», и одна из
трёх всё равно отстала: `fotmob.js` уточнял минуту живых матчей безлимитным
`Promise.all` — в субботний вечер это залп на два десятка одновременных
запросов ровно там, где соседний код от этого специально защищён.

**Источник отвечает на уровне ПРАВООБЛАДАТЕЛЯ**, а не «какой канал в какую
минуту» — это его главное свойство, и из него всё остальное. Он спокойно
называет «Match TV» сразу на пять матчей, два из которых идут одновременно.
Поэтому поверх стоят три фильтра (`dropUnsound()`), все — локальная
арифметика на уже скачанных данных, без единого нового запроса:

1. один канал на два пересекающихся по времени матча — выкидываются оба,
   если EPG независимо не подтвердил один из них;
2. EPG показывает на этом канале в это время другой отслеживаемый матч;
3. EPG показывает там другой вид спорта (`isOtherSport()` в `epg.js` —
   курируемый список на десятке языков, что реально встречаются в
   плейлисте; проверка сверяется с атрибутом `stop` из XMLTV, а не гадает
   длительность).

Без фильтров живой аудит дал 21 ложную привязку из 242. Честная оговорка:
они умеют опровергать, но не подтверждать — там, где EPG пуст (а это ровно
случай Sky Sports UK, ради которого источник и добавлялся), проверить
нечем.

Единственный нечёткий шаг — имя станции от FotMob против имени канала
плейлиста. Он требует **точного** совпадения токенов (`similarity() === 100`),
а не порога 78, как у команд: источник бонусный, потерять неоднозначный
случай дешевле, чем привязать чужой канал. Страна при этом не выводится из
текста, а задаётся самим запросом — структурно исключает путаницу между
Sky UK, Sky DE и Sky IT.

Как эндпоинт нашли, почему `matchId` в нём игнорируется, что показал
пострановой аудит, какие официальные источники проверены и отвергнуты, и
почему доработку 1.3.2 откатили в 1.3.3 — в [DECISIONS.md](DECISIONS.md).
Там же — отдельная попытка закрыть тот же пробел вторым EPG-фидом
(`epg2.js`), доведённая до рабочего состояния и откатанная как костыль.

### Регрессия на матчер — `npm test`

`node --test`, без единой зависимости, без сети и без диска (`test/matching.test.js` — синтетический список передач и строка XML; `test/epg-cache.test.js` — настоящий HTTP-сервер на localhost и папка кэша во временном каталоге). Каждый негативный кейс — реальное ложное срабатывание из разделов выше, каждый позитивный — реальная трансляция, которая должна находиться. Прогон ~200 мс.

Появились из наблюдения: 6 из первых 22 коммитов чинили именно `epg.js`, и каждый раз проверка была разовым скриптом, который потом выбрасывался, — набор из полутора десятков выстраданных кейсов жил только текстом в этом файле.

**Пробел, найденный сразу же этими тестами** (и опровергающий более раннее утверждение в этом же файле, что пара `Newcastle United`/`West Ham United` матчится): кириллический заголовок с двумя «Юнайтед» не находится вообще. `«Ньюкасл»` → `nyukasl`, до `newcastle` 5 правок при допуске 3 — единственный мост это «Юнайтед», но `meaningfulTeamTokens()` вычитает слово, общее с соперником, а у West Ham оно тоже есть (и `«Вест Хэм»` → `vest`/`hem` короче порога длины 5). На живом EPG: из 16 передач со словом «Ньюкасл» 13 содержат «Юнайтед» и находятся, 3 (`«Тоттенхэм – Ньюкасл»`, `«Ньюкасл – Ливерпуль»`) — нет. Помечены `{ todo: true }`: прогон не валят, забыть не дают. Аудит 369 команд, собиравший `RU_NICKNAMES`, этот класс пропустил структурно — он проверял, есть ли пригодный токен у **английского** имени (у «newcastle» есть), а не дотягивается ли до него **русское** написание. Лечится тем же словарём (`Newcastle United` → «Ньюкасл», `West Ham United` → «Вест Хэм»).

### Известные слабые места (компромисс, не баг)

Транслитерация кириллицы — посимвольная (`normalize.js`), не официальная романизация: клубы с нестандартной англоязычной формой имени не совпадут вообще, если их нет в `RU_NICKNAMES` (`epg.js`, см. выше) — а туда попадают только подтверждённые кодом/живым поиском случаи, не полный охват. Для проверенных 369 команд всех отслеживаемых турниров разрыв закрыт полностью; для команд за пределами этого списка (сменился состав турнира, добавился новый) — калибровать по факту, если проявится, тем же методом (код находит кандидата, живой поиск подтверждает написание).

Турнир в карточке — «Страна - Лига» как на самом FotMob (`json.details.country` + `json.details.name`), а не наше русское имя из `COMPETITIONS` (то теперь используется только для строки прогресса синхронизации, «Расписание: …»). Причина: у клубов имена приходят с FotMob как есть, по-английски — если лигу подписывать по-русски, а команды по-английски, на одной карточке получается разнобой языков. Имя страны — по короткому коду FotMob (`ENG`, `RUS`, `INT`…), не ISO-3166: маленькая захардкоженная таблица `COUNTRY_NAMES` в `fotmob.js`, тем же принципом, что и сам `COMPETITIONS`. `INT` (континентальные турниры типа Лиги чемпионов) — без префикса страны.

Список турниров в `COMPETITIONS` (`fotmob.js`) захардкожен, не в `config.json` — осознанно, под одного пользователя конфиг-опция не нужна. Пробовали и обратное: диалог «Турниры» с выбором из полного каталога FotMob (558 турниров, поиск, чекбоксы) — реализовали целиком и рабочим, но пользователь сразу забраковал вживую («слишком много ненужных турниров», «фича пока не нужна») и попросил убрать. Убран полностью: `fotmob.js` → `allLeagues()`, IPC `competitions:list/get/save`, кнопка и диалог в `index.html`/`app.js`/`styles.css` — ничего не осталось даже мёртвым кодом. Если понадобится снова — эндпоинт `https://www.fotmob.com/api/data/allLeagues` (94 страны + international, `{id, name, ccode}` на турнир) уже разведан и проверен живьём, начинать пришлось бы не с нуля.

Названия в `COMPETITIONS` — английские, как у самого FotMob (`details.name`), не перевод на русский: пользователь попросил явно, заодно это совпадает с тем, что уже показывает карточка матча (та берёт `details.name`/`details.country` напрямую, см. ниже) — раньше по-русски было только это поле, использовавшееся исключительно для строки прогресса синхронизации.

Кубки/суперкубки в дефолтном списке — только для топ-5 лиг (Англия/Испания/Италия/Германия/Франция) и России, по прямой просьбе пользователя. Кубки Нидерландов, Бельгии, Португалии, Турции, Бразилии и Аргентины убраны — их лиги при этом остались. Континентальные турниры (Лига чемпионов/Европы/конференций + квалификации, Кубок Либертадорес) под это правило не подпадают — не привязаны к одной стране. Беларусь (лига + кубок) убрана целиком отдельным решением, тоже по просьбе пользователя, до этого была добавлена в рамках «Бразилия, Аргентина, Беларусь — главная лига + кубок» — то решение частично отменено. Добавлены Премьершип Шотландии (`id 64`) и 2. Бундеслига Германии (`id 146`) — единственные два турнира из присланного пользователем списка (топ-лиги + Ла Лига/Серия А/Бундеслига/Лига 1/ЛЧ/ЛЕ + горстка кубков/MLS/Эредивизи/Португалия/РПЛ/Бельгия), которых раньше не было; остальные 17 уже присутствовали.

Карточка матча слегка подсвечена цветом турнира: FotMob отдаёт свой официальный брендовый цвет прямо в ответе (`json.details.leagueColor`, есть у всех проверенных турниров, даже у самых мелких — просто нейтральный тёмно-серый `#333333`, если своего цвета нет) — прокинут как `competitionColor`/`tournamentColor` до `renderer/app.js`, там ставится инлайновой CSS-переменной `--accent` на карточку. В `styles.css` красит только левую полоску рамки (`border-left-color`) — сознательно по минимуму, после нескольких неудачных попыток (полноразмерный полупрозрачный герб-«водяной знак» в углу карточки читался плохо для тёмных гербов вроде АПЛ, потом пробовали однотонный силуэт через `mask-image` — тоже не понравилось пользователю визуально) в итоге просто убрали водяной знак совсем, оставив только рамку. Диагональная заливка фона через `color-mix()` была следующим шагом того же компромисса, но тоже впоследствии убрана по прямой просьбе пользователя — фон карточки теперь плоский (`var(--panel-2)`), без градиента вообще. Для матчей «в эфире» (`.is-live`) подсветка live-статуса красит рамку только с трёх сторон (не через `border-color` целиком) — иначе цвет турнира на левой стороне забивался бы одинаковым оранжевым у всех live-карточек разом, и они переставали отличаться друг от друга.

**Живая минута матча** (`event.clock`) — эндпоинт `leagues?id=` сам по себе её не отдаёт (только `started`/`finished`/итоговый счёт), но после списка турниров `fotmob.js` → `fixtures()` берёт из уже построенного списка только фикстуры со `status === 'inprogress'` (обычно 1–3 разом, не сотни) и точечно дёргает `matchDetails?matchId=` для каждой. Минута — `json.header.status.liveTime.short` (не `json.general.status`, там `liveTime` нет вообще — на этом споткнулись при разведке: `general.status` просто `undefined`, значение через `||`-фолбэк тогда случайно бралось из `header.status`, из-за чего сперва казалось, что рабочее поле — `general`). Значение вида `"67‎'‎"` — с невидимыми directional-mark символами вокруг апострофа, обёрнутыми вокруг цифр — очищается регэкспом до голых цифр (+ «+N» для добавленного времени) и своего апострофа.

Обновляется вместе со счётом и статусом — раз в 3 минуты, но отдельным от полного синка циклом (`sync.js` → `refreshScores()`, см. «Два цикла обновления» ниже), не вместе с пересборкой всего расписания.

Стадион (`event.venue`) через `matchDetails` не запрашивается — тот же принцип, что и раньше (венью нужен был бы такой же отдельный запрос ради небольшой пользы), строка стадиона просто не выводится, рендерер это обрабатывает штатно.

## Тяжёлый этап в рабочем потоке

Скачивание EPG, разбор фида, сопоставление и отсев заявок вещателей — это несколько секунд сплошной синхронной работы (~850 мс разбор, ~2.8 с сопоставление). В main-процессе это напрямую морозило окно: рисует его свой процесс, а ввод и IPC обслуживает main.

Разложено так:

```
main (electron/sync.js)          поток (electron/sync-worker.js → epg-stage.js)
  плейлист                          скачать EPG
  расписание FotMob                 разобрать фид
  имена станций (tvlistings)  ──→   сопоставить матчи с каналами
                                    отсеять заявки вещателей
  сборка guide.json           ←──   { epgByFixture, extraBroadcasts, stats }
```

В main остаётся **только сеть к FotMob** — ей нужен `net.fetch` стека Chromium, которого в потоке нет. EPG-фид качается обычным `fetch` прямо в потоке: это ссылка провайдера пользователя, не защищённый от ботов API.

**Почему сеть вещателей идёт раньше разбора**, хотя логически она вторична: фильтры `dropUnsound()` спрашивают у разобранного EPG, что реально шло на канале, — значит они обязаны жить рядом с ним, в потоке. Поэтому main сперва добирает имена станций по сети и передаёт их внутрь. Это единственное место, где порядок стадий продиктован границей потоков, а не предметной областью.

Через границу едет мало: внутрь — каналы, фикстуры и имена станций, наружу — `Map` с id каналов на матч. **Именно `Map`, а не объект**: structured clone переносит его как есть, с ключами любого типа, тогда как объект привёл бы их к строкам. Здесь до 01.09.2026 стояло обоснование «ключи-id матчей числовые» — оно неверно, id матчей у FotMob строковые (проверено у источника: `m.id` в `leagues?id=` и ключи `tvlistings` одного типа), так что объект сработал бы тоже. `Map` оставлен ради независимости от типа: смени FotMob его на одной из сторон — объект молча схлопнул бы ключи, и `dropUnsound()` не нашёл бы ни одного матча, не выдав ни единой ошибки. По той же причине сохранена таблица `realId` в `claimsFromStations()` — она не переводит тип (переводить нечего), а отбрасывает заявки на матчи не из нашего списка, у которых нет `start`.

Логика этапа вынесена в `epg-stage.js` отдельной функцией, а сам воркер — десяток строк передачи сообщений: этап так можно вызвать и проверить напрямую (`test/epg-stage.test.js`), без потоков.

Результат: блокировка интерфейса за синк **2782 → 64 мс**, память после синка **172 → 95 МБ** (изолят потока сносится вместе со всем, что он держал). Проверено и на упакованной сборке — воркер грузится из `app.asar` штатно.

## Два цикла обновления: расписание отдельно от счёта

Раньше был один цикл на всё — каждые 3 минуты (и по кнопке «Обновить») `sync.run()` пересобирал вообще всё: заново дёргал все ~55 турниров у FotMob, заново качал/парсил EPG (хоть и с 6-часовым диском-кэшем самого файла), заново гонял сопоставление команд с каналами по всем ~16–46 тысячам передач. Расписание и список каналов меняются медленно — пересобирать их каждые 3 минуты не было смысла, а вот счёт/статус/минута у уже найденных матчей за 3 минуты успевают устареть. Пользователь попросил развести это на два независимых цикла.

**Полный синк** (`sync.js` → `run()`, IPC `guide:sync`, кнопка «Обновить») — без изменений по сути, просто реже: при запуске приложения, раз в час (`setInterval` в `app.js`) и по клику — качает все турниры, всю EPG, пересчитывает сопоставление с нуля, пишет `guide.json` целиком.

**Лёгкое обновление счёта** (`sync.js` → `refreshScores()`, IPC `guide:refreshScores`) — раз в 3 минуты, тем же интервалом, что раньше был у полного синка, но теперь отдельным вызовом. Не трогает FotMob-турниры списком и не трогает EPG вообще — берёт уже готовый `guide.json`, отбирает события, у которых `start <= now` и `status !== 'finished'` (то есть уже начавшиеся и ещё не завершённые — как правило это ровно те же 1–5 матчей, что и «живые» для минуты), и для каждого точечно дёргает `matchDetails?matchId=` (`fotmob.js` → `matchStatus()`, который заменил собой более узкую `liveClock()` — тот же эндпоинт, просто теперь отдаёт статус/счёт/минуту разом, а не только минуту). У матча, который ещё не начался (`start > now`), при таком отборе нет вообще никакого сетевого запроса — его `start` уже говорит всё, что нужно знать, до самого удара по мячу.

Матч, ставший `finished` во время лёгкого обновления, **удаляется из гида** тем же проходом (то же правило «только живое и предстоящее», что и в `run()`), а не ждёт следующего полного синка — иначе он бы зависал в списке лишний час. `guide.generatedAt` при лёгком обновлении не трогается — оно означает «последний полный синк расписания», а не «последнее любое изменение»; статус-строка в интерфейсе тоже не обновляется на каждый тик (`renderer/app.js` → `doScoreRefresh()` работает тихо, без сообщений и без блокировки кнопки «Обновить» — виден только результат: тикающий счёт, появляющийся бейдж LIVE, пропадающая завершённая карточка).

Проверено живьём (`sync.refreshScores()` напрямую): матч, который на деле оказался `finished`, корректно выпадает из гида целиком вместе с турниром, если это был единственный матч в нём; матч с `start` в будущем не трогается ни разу, ни одного лишнего запроса.

## Избранное и уведомление о начале матча

Звёздочка в углу карточки (`renderer/app.js` → `starButton()`) добавляет матч в избранное — список id хранится в `favorites.json` (`electron/favorites.js`, тот же паттерн, что и `guide.json`: плоский JSON через `store.js`, без базы данных). Ключ — `event.id`, он же id матча от FotMob (`f.id` в `sync.js`), стабилен между синками, пока матч остаётся в отслеживаемом окне дат. IPC `favorites:get`/`favorites:toggle` — сохранение уходит в main-процесс (рендерер не пишет на диск напрямую), но сам список держится в рендерере как `Set` и синхронизируется локально сразу после клика, без ожидания следующего рендера всей ленты.

Клик по звезде останавливает всплытие (`e.stopPropagation()`) — иначе сработал бы обработчик клика по всей карточке (`play()`, запуск VLC). Звезда — `position: absolute` поверх правого верхнего угла карточки; у `.card-top` добавлен `padding-right`, чтобы длинный бейдж («LIVE · 90+5'») не наезжал на неё — проверено вживую скриншотом на реальном запуске.

Уведомление о начале — не отдельный сервис-воркер и не таймер в main-процессе: та же модель, что у `doScoreRefresh()` (см. «Два цикла обновления» выше) — рендерер и так уже единственное, что живёт, пока живо окно (`window-all-closed` завершает `app` целиком, фонового режима без окна нет), так что таймер в рендерере ничем не хуже таймера в main, но не требует лишнего IPC. `checkFavoriteKickoffs()` в `app.js` крутится раз в 30 секунд, зовёт `new Notification()` (обычный Web-API, Electron поддерживает нативно в рендерере даже с `contextIsolation: true`/`nodeIntegration: false` — это не завязано на Node-интеграцию) для каждого избранного матча, чей `start` попал в последние 90 секунд (окно троекратно больше периода опроса — запас на дрожание таймера, не подгонка под конкретный баг). Уже уведомлённые матчи держатся в `Set` в памяти рендерера, не на диске: если приложение было закрыто ровно в момент старта матча, при следующем запуске уведомление специально не досылается «задним числом» — «матч начался 2 часа назад» ничем не поможет, а окно в 90 секунд и так исключает такую ситуацию при живом сеансе.

## Плеер: VLC вместо hls.js

`hls.js` не смог воспроизвести часть потоков (interlaced 1080i H.264 — `mux.js` зависает при перемультиплексировании в fMP4 для MSE, без единой ошибки, просто чёрный экран). VLC тот же поток играет нормально (нативный декодер, не через MSE браузера) — проверено вживую. Пользователь предпочёл полностью заменить встроенный плеер на VLC вместо разбора, у каких потоков конкретно проблема.

Первая версия «пришвартовывала» окно VLC внутрь окна приложения и тянула за
собой хвост Win32-грабель; почему от докинга отказались в пользу двух
независимых окон — в [DECISIONS.md](DECISIONS.md).

### Грабли, вживую найденные при подключении VLC

Актуальны и для текущей модели (без докинга) — они про сам процесс/CLI VLC, а не про синхронизацию окна.

**`--play-and-exit=no` — невалидный синтаксис.** VLC не принимает `=no`/`=yes` для булевых флагов, только `--no-play-and-exit`. С неверным флагом VLC падал на старте ещё до открытия окна — процесс появлялся и тут же исчезал, выглядело как «зависание», а на деле `vlc: unknown option` в stderr.

**VLC разворачивается на весь экран уже ПОСЛЕ старта воспроизведения**, а не при создании окна — судя по всему, из-за личных настроек VLC пользователя (сохранённое «включить на весь экран» в его `vlcrc`). `--no-fullscreen` и `--no-qt-video-autoresize` не помогли перебить это сами по себе. `SetWindowPos` при этом каждый раз возвращал `true` (успех), но реальная геометрия окна оставалась (0,0,ширина_монитора,высота_монитора) — признак того, что окно в состоянии `WS_MAXIMIZE`, для которого Windows игнорирует размер/позицию из `SetWindowPos`, пока не восстановить его явно.

**Фикс — двухчастный:** (1) `ShowWindow(hwnd, SW_RESTORE)` непосредственно перед каждым `SetWindowPos`, снимает maximized-состояние; (2) этого мало на один раз — VLC переразворачивается через ~1 секунду после старта декодирования, так что позиционирование переустанавливается ещё несколько раз в первые ~3.5 секунды сразу после запуска (`play()` → цикл `setTimeout` на 300/700/1200/2000/3500 мс), пока не «устаканится». После этого окно уже никто не трогает — оно в полном распоряжении пользователя.

**Моргание окна при переключении канала (актуально и сейчас).** Изначально `play()` каждый раз убивал старый процесс VLC и поднимал новый — пересоздание окна ОС и было причиной моргания. Фикс: VLC запускается с `--extraintf=http --http-port=... --http-password=...` (loopback, случайный пароль на процесс), при живом `current` `play()` просто шлёт `pl_empty`+`in_play` через это HTTP-API вместо перезапуска процесса.

**Ошибка `spawn()` приходит СОБЫТИЕМ, а не исключением — и без слушателя роняет главный процесс.** Слушателя `'error'` на дочернем процессе не было, и асинхронный провал запуска (ENOENT) превращался в необработанное исключение: Electron показывает пользователю модальное окно «A JavaScript error occurred in the main process» со стеком. Достижимо буднично, без всякой экзотики: путь к VLC лежит в конфиге, а сам VLC потом удалён, перенесён или находится на отключённом сетевом диске — `existsSync()` в `findVlcPath()` проверяет файл заранее, но между проверкой и запуском есть `await freePort()`. Осторожно с диагностикой: **это окно, а не строка в stderr**, поэтому grep по выводу процесса его не видит и создаёт ложное впечатление, что всё в порядке. Не путать с синхронной веткой: неисполняемый файл (`.txt`, переименованный `.exe`) даёт `spawn UNKNOWN` **броском**, который штатно ловится `try/catch` в `vlc:play` — падения там нет, проверено отдельно.

**Два быстрых клика по каналам поднимали два процесса VLC.** `current` присваивается в самом конце `play()`, уже после поиска окна циклом до десяти секунд, — всё это время второй вызов видит `current === null` и запускает свой экземпляр. Второй затирал `current`, первый оставался осиротевшим навсегда: `stop()` знает только про `current`, а обработчик `exit` у сироты сверяет `current?.child === child` и тоже молчит. Процесс переживал закрытие приложения. Лечится очередью (`queue` в `vlc.js`), а не флагом «занято»: второй клик не теряется, а дожидается конца запуска и дальше идёт обычным путём — переключением канала в уже поднятом окне. Проверено: было два процесса и один осиротевший после `stop()`, стало один и ноль.

**Цикл поиска окна отрабатывал все сорок шагов вслепую.** На неверном пути пользователь десять секунд смотрел на «Запускаю VLC…», прежде чем получить ошибку. Оба признака провала (`spawnError`, `child.exitCode`) видны уже на первом шаге — 279 мс вместо 10 секунд.

Сеть без таймаута вешала синк молча и навсегда — кнопка «Обновить» заблокирована, отменить нечем. Таймауты стоят на всех четырёх точках: FotMob (20 с, `net.js`), EPG-фид (120 с — он весит десятки мегабайт, таймаут не про «медленно», а про «повисло»), плейлист по ссылке (30 с). Кэш EPG чистится сам: файлы разведены по URL (`epg-{sha1}.xml.gz`), протухшие чужие удаляются после успешной закачки новой — иначе они копятся навсегда (на машине автора накопилось 170 МБ от четырёх провайдеров, а в упакованной сборке это растёт в `%APPDATA%` у каждого, кто менял источник). Битый файл кэша (оборванная запись) не блокирует синк на все шесть часов TTL — распаковка в `try`, при провале файл выкидывается и качается заново.

`config.json` в корне репозитория — личный рабочий конфиг пользователя (реальные пути плейлиста/EPG), в git не попадает (см. «Безопасность»). Закоммичен только пустой шаблон `config.example.json` — его же теперь пакует `electron-builder` (`build.files` в `package.json`) и с него же стартует `ensureConfig()` при первом запуске что в dev, что в упакованной сборке. Раньше `config.json` паковался как есть, поэтому перед каждым `npm run dist` его приходилось вручную зануля́ть и восстанавливать после — с шаблоном это больше не нужно.

Зависимости: `electron` и `koffi` (нативный биндинг для Win32-вызовов — единственное исключение из «нет нативных модулей», обосновано в разделе про VLC). `hls.js` удалён вместе со встроенным плеером. База данных не нужна — кэш лежит JSON-файлами.

## Диалог «Настройки» — плейлист, EPG, VLC, турниры в одной точке входа

Изначально назывался «Источники» и отвечал только за плейлист/EPG. Пользователь попросил переименовать в «Настройки», когда в тот же диалог добавился чек-лист турниров (см. ниже) — под новым содержимым старое имя уже не подходило. IPC переименован вслед за диалогом: `sources:get`/`sources:save` → `settings:get`/`settings:save`.

Раньше плейлист выбирался только файлом (диалог ОС), а EPG — только неявно, через `url-tvg` внутри самого плейлиста (оверрайд был, но только правкой `config.json` руками). Пользователь попросил разделить: у плейлиста и EPG независимые поля, и оба могут быть либо локальным файлом, либо прямой ссылкой.

`electron/playlist.js`: `parse(path)` (только файл) заменён на `parseText(text)` (чистый разбор строки, без источника) + `load(source)` (async; `source` — файл или `http(s)://`-ссылка, определяется `isUrl()`). Для URL — обычный `fetch` (не `electron.net.fetch`): это ссылка из собственной подписки пользователя у своего же IPTV-провайдера, а не публичный API с защитой от ботов, так что спецстек Chromium тут не нужен — тот же выбор, что уже был сделан для EPG-фида в `epg.js`. Кэша на диске для плейлиста нет (в отличие от EPG-фида, который весит 30–170 МБ) — и раньше локальный файл перечитывался с нуля при каждой синхронизации, свежий фетч по URL — та же по цене операция, не новая.

`electron/paths.js` → `resolvePlaylist()` пропускает `http(s)://`-строки как есть, не пытаясь склеить их с `dataDir` как путь.

`playlist:choose` остался отдельным IPC — просто открывает диалог выбора файла и возвращает путь, без побочного сохранения в конфиг; сохранение всегда через `settings:save`, единой точкой.

`vlcPath` раньше можно было переопределить только правкой `config.json` руками (см. `vlc.js` → `findVlcPath()` — без оверрайда перебирает пару стандартных путей `Program Files`). Первая попытка добавила для этого отдельный диалог рядом с «Источниками» — пользователь сразу попросил объединить обратно в одну точку входа, не плодить диалоги ради одного поля. Путь к VLC — третье поле в том же диалоге, тот же паттерн, что у выбора плейлиста — IPC `vlc:choose` (диалог выбора файла, фильтр `.exe`, без побочного сохранения). `settings:save` проверяет `fs.existsSync()` для `vlcPath` перед записью (в отличие от `playlistPath`, это поле необязательное — пустая строка не ошибка, а сброс к автоопределению, ключ не пишется в JSON).

### Чек-лист турниров

Не путать с уже пробованным и убранным диалогом «Турниры» (выбор из полного каталога FotMob, 558 турниров, см. историю чуть выше) — тот требовал сетевого запроса и поиска по огромному списку, пользователь его забраковал. Этот чек-лист — принципиально другое, гораздо меньшее по объёму: всего лишь возможность **включать/выключать** турниры из уже существующего кураторского списка `COMPETITIONS` (39 записей), прямо в «Настройках», без похода за полным каталогом FotMob.

Каждая запись `COMPETITIONS` в `fotmob.js` получила поле `country` (группа FotMob, тот же источник, что и раньше сверяли вручную через `allLeagues`) — статика, без сетевого запроса при открытии диалога, в отличие от убранного диалога «Турниры». Рендерер (`renderer/app.js` → `renderCompetitionsList()`) группирует по `country`, International — первой группой, остальные по алфавиту, тот же порядок, что и в каталоге FotMob.

`config.json` → `disabledCompetitions`: список **выключенных** id (не включённых!) — так отсутствие поля означает «ничего не выключено», то есть ровно прежнее поведение для уже существующих конфигов, без нужды перечислять все 39 турниров явно. `fotmob.js` → `fixtures(daysBack, daysForward, onProgress, disabledIds = [])` фильтрует `COMPETITIONS` этим списком перед синком. Проверено живьём: с явным списком «все, кроме РПЛ» синк вернул только РПЛ; без списка вообще (`undefined`) — прежние 246 фикстур по 23 турнирам, ничего не сломалось.

Валидации «выбери хотя бы один турнир» нет (в отличие от `playlistPath`) — весь чек-лист виден пользователю прямо в диалоге, который он редактирует, так что случайно выключить всё и не понять почему пусто — не тот риск, что был с фоновым EPG-кэшем или скрытым выбором из 558 позиций.

## Работа с любым провайдером плейлиста/EPG

Изначально всё (парсинг группы, отбор «спортивных» каналов, таблица группа→страна) было откалибровано под одного конкретного провайдера. Пользователь явно попросил научиться работать с чужими плейлистами тоже — проверено на живом примере другого провайдера (Antifriz, `#EXTM3U ... url-tvg="http://tchaikovsky.af-stream.com:8080/epg.xml.gz"`, `tvg-id="nash-futbol-hd-orig"` — заметно другой стиль id, чем числовые `chNNNN` у текущего). Сделано три вещи:

1. **Группа канала** — раньше бралась только из отдельной строки `#EXTGRP:` (особенность текущего провайдера). Теперь `playlist.js` сперва читает стандартный атрибут `group-title=""` прямо в `#EXTINF` (то, что понимают «обычные» плееры/парсеры), а `#EXTGRP:`, если он тоже есть, просто переопределяет — так у текущего провайдера ничего не поменялось (у него `group-title` нет вообще), а у провайдеров со стандартным M3U это заработало.
2. **Отбор «это матч или нет» — без привязки к «спортивным» каналам вообще**, см. `epg.js` → `programmes()` выше: раньше был обязательный предфильтр по группе/имени, откалиброванный под текущего провайдера («9. Sport/Спорт» с номером) и ломавшийся на другом стиле («Спорт» без номера у Antifriz). Убран целиком — сканируются все каналы, что есть в плейлисте, а не только «похожие на спортивные».
3. **Формат EPG-фида по содержимому, не по URL** — `epg.js` → `loadXmltv()` понимает как есть: обычный `.xml`, `.xml.gz`, и `.xml.tar.gz` (gzip-сжатый tar с одним XML-файлом внутри — без библиотеки, свой мини-`untar()` на 512-байтные заголовки, достаточно для «достать один файл из одного архива»). Определяется по магическим байтам после распаковки (ведущий `<` — это XML, иначе распаковывается как tar), а не по расширению в ссылке — так что неважно, какой конкретно вариант отдаёт провайдер.

**Что осталось провайдер-специфичным осознанно** (не блокирует основной сценарий, деградирует тихо): таблица «номер группы → страна» (`GROUP_COUNTRY` в `playlist.js`) — она нужна только для маленького флажка-страны на чипе канала; для незнакомой схемы групп страна просто останется `null` (чип без флажка), это не мешает найти и воспроизвести трансляцию. Префикс имени вида `UK:`/`IT:` — уже достаточно общий паттерн, отдельной калибровки не потребовал.

**Кэш EPG разведён по URL** (`epg-{sha1(url)}.xml.gz`) — иначе при смене
провайдера в пределах 6-часового TTL отдавался бы старый фид с чужой схемой
`channel id`, и сетка молча оказывалась пустой без единой ошибки. Разбор
того случая — в [DECISIONS.md](DECISIONS.md).

## Грабли, на которые уже наступали

**У приложения не было последнего рубежа для необработанных ошибок.** Ни `uncaughtException`, ни `unhandledRejection` — то есть любая непредвиденная асинхронная ошибка в main показывалась пользователю тем самым модальным окном со стеком. Теперь оба обработчика есть (`main.js`), пишут в `console.error` и дублируют короткое сообщение в строку статуса окна — на Windows GUI-процесс Electron ненадёжно печатает в родительскую консоль, так что одного `console` мало. Из процесса при этом **осознанно не выходим**: канон «упавший процесс в неизвестном состоянии надо перезапускать» писан для серверов, где процесс безлик и поднимется сам; здесь его падение — это исчезнувшее окно у человека, который смотрит матч, а всё важное (сетка, избранное) уже на диске и пишется атомарно. Сам `send()` внутри обработчика — обязательно в `try`: у закрытого окна он бросает «Object has been destroyed», а бросок из обработчика необработанных исключений даёт ровно то окно с ошибкой, ради которого всё затевалось.

**Падение подготовки данных оставляло приложение невидимым висящим процессом.** `ensureConfig()`/`setRoot()`/`migrateFavorites()` стояли в `app.whenReady()` голыми, до `createWindow()`. Если любая из трёх бросала (нет места, права на `%APPDATA%`, шаблон конфига не попал в сборку), окно не создавалось вообще — а `window-all-closed` при этом не срабатывает, потому что окон и не создавали, так что закрыть приложение можно было только через диспетчер задач, и никакого сообщения пользователь не видел. Теперь три строки в `try`, а `createWindow()` выполняется при любом исходе: с пустым конфигом окно честно покажет «Плейлист не выбран» и даст открыть «Настройки». Проверено имитацией броска из `ensureConfig()`.

**Тяжёлые синхронные циклы в main-процессе морозят окно.** Рисует окно свой процесс, а ввод и IPC обслуживает main — пока он занят, приложение выглядит зависшим. Сопоставление держало его 2.8 секунды подряд, разбор фида — ещё 850 мс. Решено границей потоков, а не уступками: весь тяжёлый этап уехал в `worker_threads` (см. «Тяжёлый этап в рабочем потоке» ниже). Пробовали и промежуточный вариант — рассыпать по циклам `await`-уступки event loop'у: работало (2782 → 452 мс), но протаскивало планирование в сигнатуры чистых функций, включая тесты. Откачено в пользу воркера.

**Ускорять разбор бессмысленно, профилировано**: горячей точки нет — 110 мс на поиск границ тегов, 60 на срезы в строки, остальное размазано по 424 тысячам передач. Предкомпиляция регулярок в `attr()` экономит 20 мс из 855, а «очевидно быстрый» разбор даты по позициям вместо регулярки оказался **вдвое медленнее**.

**`worker.terminate()` надо дожидаться.** Поток — не процесс: изолят живёт в том же процессе, и пока он не снесён, его 200-мегабайтный буфер числится за приложением. Без `await terminate()` синк «заканчивался» на 309 МБ вместо 95.

**Как мерить блокировки и НЕ обмануться** — на этом я попался трижды: (1) `setInterval` не видит синхронный блок вообще, если `clearInterval` стоит в том же блоке — таймер просто не успевает сработать ни разу, и разрыв показывается нулевым; надо дать ему сработать (`await setTimeout(300)`) до снятия; (2) сбрасывать точку отсчёта прямо перед уступкой — значит измерять не блокировку, а интервал между сбросами (так у меня вышло «66 мс» вместо настоящих 810); (3) для пика памяти всё то же самое, см. раздел про побайтовый разбор. Надёжно — только синхронные контрольные точки вокруг стадии.

**Нельзя называть свою папку в `userData` словом `cache`.** Chromium держит дисковый HTTP-кэш ровно в `userData/Cache`, а пути на Windows регистронезависимы — то есть `userData/cache` и `userData/Cache` это одна и та же папка. Наши `guide.json`, `favorites.json` и скачанный EPG лежали там же, где `Cache_Data/data_0…data_3` и `index`, и Chromium вычищал их при своей уборке. Снаружи: после перезапуска расписание «сбрасывается» (кэш считается отсутствующим, показывается «Сетки пока нет»), EPG качается заново каждый запуск вместо шести часов TTL, избранное пропадает. **В dev-режиме баг не воспроизводится вообще** — там наши файлы идут в папку проекта, а кэш Chromium в `%APPDATA%\Electron`, и они не пересекаются; ловится только на собранном приложении. Папка теперь `userData/data`, инвариант стережёт `test/paths.test.js` (падает, если имя вернуть в список тех, что создаёт Chromium).

`Sec-Fetch-*`, `Origin` и `X-Requested-With` — запрещённые имена заголовков. Chromium выставляет их сам и бросает исключение при попытке задать вручную. Выглядит как сетевая ошибка.

Атрибут `hidden` перебивается любым правилом вида `.bar { display: flex }`. В `styles.css` для этого стоит `[hidden] { display: none !important; }` — не удалять.

На Windows GUI-процесс Electron ненадёжно печатает в родительскую консоль, поэтому все диагностические скрипты дублируют вывод в `*.log` рядом с `package.json`.

VPN ломает всё: Cloudflare режет датацентровые диапазоны. Если внешние запросы вдруг отдают 403 на всё подряд — первым делом проверить туннель.

Если `ELECTRON_RUN_AS_NODE=1` стоит в окружении, `electron.exe` запускается как обычный Node — `require('electron')` возвращает путь строкой вместо модуля, и `app.isPackaged` в `paths.js` падает с `TypeError: Cannot read properties of undefined`. Перед обычным запуском (`electron .`) убедиться, что переменная снята (`Remove-Item Env:\ELECTRON_RUN_AS_NODE` в PowerShell) — она же, наоборот, нужна, если хочешь прогнать какой-то `.js`-файл через связанный с проектом Node без `npm`/`node` в PATH.

(Sofascore-специфичное: расписание за соседние даты перекрывалось, события у полуночи приходили дважды — решалось дедупликацией по `id`. У EPG-конвейера дублей такого рода нет: `sync.js` берёт даты прямо из `event.start` вместо запроса по окну дат, а показы одного матча на разных каналах и так сводятся в одну карточку — `epg.findBroadcastChannels()` сама возвращает список всех подходящих `channelId` для одной фикстуры.)

## Автообновление и публичный репозиторий

Репозиторий публичный — именно ради того, чтобы `electron-updater` работал
без токена внутри собранного приложения. Что проверяли перед публикацией
(аудит всей git-истории на секреты, переписывание email автора коммитов) —
в [DECISIONS.md](DECISIONS.md).

**Как устроено само автообновление** (`electron/main.js`): `package.json` → `build.publish` — `{ provider: 'github', owner, repo }`, без токена, без доп. полей. `checkForUpdates()` вызывается один раз при старте (`app.whenReady()`, после `createWindow()`), но только если `app.isPackaged` — в dev-режиме (`npm start`) проверка не имеет смысла (нет запакованной версии для сравнения) и молча пропускается, что и подтверждено живым прогоном (`npm start` → в логе никаких обращений к update-API, баннер не появляется). `autoUpdater.on('update-downloaded', …)` шлёт `update:ready` в рендерер только когда файл уже полностью скачан — без промежуточного состояния «ищу»/«качаю», подряд один тихий баннер «Доступна версия X» с кнопкой «Перезапустить» (`ipcMain.handle('update:install', () => autoUpdater.quitAndInstall())`). Ошибка проверки (сеть, GitHub недоступен) просто логируется и молча откладывается до следующего запуска — та же философия отказоустойчивости, что и у обычного синка.

`npm run dist` без явного флага `--publish`/переменной `GH_TOKEN` не пытается ничего публиковать сам — проверено живьём после добавления `publish`-конфига, сборка проходит как раньше, релиз по-прежнему заливается вручную через `gh release create` (важно не забыть в этот процесс `latest.yml` из `dist/` — без него `electron-updater` не находит фид обновлений на GitHub Release).

Добавление `electron-updater` не привнесло ни одной новой уязвимости в `npm audit` — все 9 high + 1 critical, что показывает `npm audit`, унаследованы от уже существующей связки `electron`+`electron-builder` (инструменты сборки, не то, что попадает в собранное приложение), проверено сравнением `npm audit` до и после добавления зависимости (тот же счётчик).

## Безопасность

`playlist.m3u8` содержит токен доступа в URL каждого канала. Файл в `.gitignore` — не коммитить, не показывать в выводе целиком.

`config.json` тоже в `.gitignore` — хранит личный путь к плейлисту пользователя (и, потенциально, EPG-ссылку с чувствительными параметрами). В git — только пустой шаблон `config.example.json`.
